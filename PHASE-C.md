# JURIS-UQ — Phase C: statute store and context packs

Phase C turns the project's temporal claims into table lookups: a statute
table with validity intervals, a link table with relation types, a loader,
and a context builder that attaches the relevant entries to a stored Phase A
record under the registered field `record['context']`. Nothing in it learns.
Implements the engineering specification v2, section 15 (interfaces, schema
and acceptance tests are exactly as specified there).

---

## 0. What is in this drop


script 20 from `table.py`, so the file on disk can never drift from the code
(the sha256 is printed and stored in a manifest).

## 5. What the numbers mean (read before interpreting)

* **Coverage 0.689 is the honest number, not a defect.** 611 unique asserted
  provision references in the frozen run; the store answers for 421. The 190
  unknowns are long-tail provisions (robbery IPC 395/396, hurt IPC 324, …)
  the scoped table deliberately does not carry. The spec's rule: *unknown is
  never False* — an unknown provision contributes no stale-law verdict, and
  the report says exactly how much of the assertion mass was covered, so no
  temporal factor can ever be quoted as if it covered 100 %.
* **`in_force: None` ≠ stale.** `None` means the store has never heard of the
  key; `False` means the provision existed and was repealed. Phase D reads
  these differently.
* **`crosswalk_relation` is `successor_of` for all 200 items** — every item's
  trap provision is the declared predecessor of its gold provision, i.e. the
  context pack confirms the slice's own construction, independently of the
  model.

## 6. The one human task (about an hour, do it before Phase D quotes anything)

Every row ships `verified: false`. Script 22 runs the verification pass as a
checklist; the generated JSONL is never hand-edited.

```powershell
# 1. export the checklist (48 rows, one per statute)
python scripts\22_verify_statutes.py --export
#    -> data\statutes\verification_checklist.csv

# 2. open the CSV next to the official texts (India Code gazette + the
#    Schedule to the Bharatiya Nyaya Sanhita, 2023). For each row:
#      - compare text_excerpt, successor, predecessor with the official text
#      - set verified_ok to yes or no
#      - fill official_source (citation you checked) and notes if needed

# 3. apply the checklist (rewrites the overrides file)
python scripts\22_verify_statutes.py --apply
#    -> data\statutes\statutes_v1.overrides.jsonl

# 4. rebuild the table; verified flags take effect, the hash changes
#    (expected) and the manifest reports the new verified share
python scripts\20_build_statutes.py --out data\statutes\statutes_v1.jsonl
```

Changing a `yes` back to `no` (or clearing it) and re-running steps 3–4
removes the flag again: `--apply` rewrites the whole overrides file from the
checklist, so the CSV is the single human-editable source of truth and
regenerating the table can never erase verification work.

One row is *known* to need this review: the frozen crosswalk maps
`IPC 506 -> BNS 351(2)`, while the official Schedule places criminal
intimidation at BNS 351(4)–(5). The store mirrors the frozen slice and the
row is flagged — which is exactly what the `verified` field exists for.
The Phase C results note (`PHASE-C-RESULTS.md`) reports the verified share.

## 8. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `ModuleNotFoundError: jurisuq` | run from a subfolder | run from the repo root (scripts add the root to `sys.path`) |
| `ERROR: statute table not found` | script 20 not run yet | run Step 1 first |
| `ERROR: no such run: ...items.jsonl` | wrong `--run-id` or `--runs-dir` | the message lists the available run folders |
| `ERROR: <out> already exists` | re-running step 3 | add `--force` or a new `--out-suffix` |
| sha256 is `4E1640E6…` on Windows | pre-patch writer translated LF to CRLF | content is identical — see section 10, apply patch 1 and rebuild |
| sha256 differs otherwise | you edited `table.py`, or overrides are applied | expected — record the new hash in your results note |
| verified flags disappeared after re-running 20 | table regenerated without overrides | keep `statutes_v1.overrides.jsonl` (written by script 22); 20 applies it automatically unless `--no-overrides` |
| `SOURCE RUN CHANGED` (exit 2) | something wrote into the frozen run | restore the run from git / re-clone; investigate before trusting the report |

## 10. Windows line endings and the sha256 mismatch (resolved, patch 1)

**What was observed.** The first Windows build of the table produced
sha256 `4e1640e668b6414542abfc0554cfecb4285c02c2504d240335fcc78e914a6d00`
where this document expects
`7be783e38c21effb24734a8be5400b9bd0c358d63130bb896aa13220ea09b61f`.

**Diagnosis (byte-level, reproduced).** The two hashes are the same 48 rows
with different line endings. The pre-patch writer used
`Path.write_text(...)`, whose default text mode translates every `\n` to
`\r\n` on Windows; on Linux/macOS it writes `\n`. Re-encoding the identical
generated payload both ways reproduces *both* hashes exactly — CRLF gives
`4e1640e6…`, LF gives `7be783e3…`. All semantic output was unaffected, which
is why every downstream number matched: JSON parsing tolerates carriage
returns, so the CRLF table loaded and packed identically (same 611/421/190
coverage figures).

**Fix.** All Phase C writers now pass `newline="\n"` explicitly (scripts 20,
21 and 22), so the artefacts — and their hashes — are byte-identical on every
platform. `tests/test_context.py` pins this: the table must contain no `\r`
and must hash to the canonical value, so a regression cannot ship silently.
The expected hash above was *not* changed: it was the correct value all
along; the writer was wrong.

**What to do if you have a pre-patch table.** Nothing is lost. Apply patch 1,
re-run script 20, and confirm `Get-FileHash` now prints `7BE783E3…`; then
re-run script 21 with `--force` so the `+ctx` run's recorded
`statutes_sha256` points at the rebuilt table (the pack contents are
unchanged).

## 9. Scope discipline (why 48 rows)

The store covers the ten offence clusters of the frozen slice and the
provisions those clusters touch — including the provisions the frozen run
actually asserted most often (IPC 378 alone appears 200 times) — *not* Indian
criminal law. Growing the table is a data edit in `table.py` plus a rerun of
script 20; the validator (schema, boundary dates, symmetric links, cluster
membership) refuses to write an inconsistent table, and every row keeps its
own `verified` flag.
